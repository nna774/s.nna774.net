# 既知の課題（判断待ち）

対応するかどうかまだ決めていない既知の課題を並べる。ここに載っているのは
「バグとして今すぐ直す」ではなく「気づいてはいるが優先度・方針を保留して
いる」もの。

## 消えたはずのデータが DynamoDB に残り続ける

タイムラインには出てこないが、受信・削除処理の掃除漏れで DynamoDB に
残り続けているデータがいくつかある。

### 1. 自分の投稿を消しても Like / Announce の記録が残る

`deleteStatusHandler`（`status.go`）は自分の投稿本体と outbox は消すが、
その投稿に付いていた `KVLikes` / `KVAnnounced`（`page.go` でいいね数・RT数
や `/status/:id/likes`・`/status/:id/announces` の一覧に使っている）は消さ
ない。投稿自体が 404 になった後も、誰がいいね・RT したかのキーだけ残り、
二度と参照されない。

- 現状: 掃除していない
- 対応案: `deleteStatusHandler` で投稿削除時に `KVLikes` / `KVAnnounced` も
  対象の URI で削除する
- 優先度感: 低め。実害は「消えたデータが少し残る」程度で、表示や動作に
  影響しない

### 2. 相手アカウントが退会した後も、その人が付けた Like / Announce が残る

`isTombstoneDelete`（`inbox.go`）は退会（Actor 自身への Delete）を受けると
`KVFollowers` / `KVFollowing` からは消すが、その相手が過去に自分の投稿へ
付けた `KVLikes` / `KVAnnounced` は消えない。`undoHandler` の Undo(Like) /
Undo(Announce) はちゃんと該当レコードを消しているので、同じことを退会の
経路でもやるべきところが漏れている。

- 現状: 掃除していない
- 対応案: `isTombstoneDelete` の分岐で、退会した actor をキーに含む
  `KVLikes` / `KVAnnounced` も走査して削除する（ただし現状のテーブル設計
  では「その actor が付けた分」を actor 起点で引く索引が無く、全件走査に
  なる。索引を足すかどうかも合わせて検討）
- 優先度感: 1 より高い。消えたはずの人の痕跡が残り続けるのは、退会の
  意味合い（本人がフェディバースから居なくなること）に対してズレがある

### 3. タイムラインの走査上限を超えた古い投稿への Delete が効かない

`removeFromTimeline`（`inbox.go`）は直近 `timelineScanLimit`（500件）しか
遡らない。それより古い投稿に対して Delete が届いても対象が見つからず、
タイムライン上にそのまま残り続ける（1・2 とは逆に「消されたはずのものが
消えない」形の取りこぼし）。

Mastodon 本体はここに相当する制約が無い（RDB で URI に索引を張って直接
引けるため）。うちの 500 件走査は DynamoDB の連番キーだけで持っている
（URI からの逆引き索引が無い）ことに由来する実装都合の妥協であり、一般的
な fediverse 実装の作法ではない。

- 現状: 対応していない
- 対応案: KV テーブルに「object URI → タイムライン連番」の逆引きレコード
  を足し、`removeFromTimeline` を走査ではなく直接引きにする
- 優先度感: 低め。投稿自体は残るだけで実害は小さい

### 4. 通知テーブルが無制限に積み上がる

`notification`（連番キー、`notification.go`）は削除する経路が無く、無制限
に積み上がる。`/notifications` ページでは見える（ページングで遡れる）が、
既読判定・Delete 連動判定はどちらも直近 `notificationScanLimit`（500件）・
`unreadCountLimit`（100件）までしか遡らないため、それより古い分は取得は
できても状態の整合が取れなくなる。

- 現状: 対応していない
- 対応案: 未定（古い通知を消す／別ストレージに退避する／整合判定用の索引
  を足す、などいくつか方向がある）
- 優先度感: 保留。1人用インスタンスでここまで積み上がるかどうか自体、
  実際の運用量次第
